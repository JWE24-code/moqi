# 0.5 — Permissions & Memory

Two features, built entirely in moqi on seams the Harness already exposes. No
Harness changes.

## What the Harness already gives us

- **Approvals** (`dsh-user-approval`): one-shot by design. Policy is
  `ask | never`; outcomes are `allowed-once | rejected | cancelled |
  unavailable`. Answerers are `approval/request` waterfall listeners — moqi's
  is at `src/index.ts` (`registerTrustSurfaces`). The request carries
  `toolName`, `callId`, and `reason`, not the arguments; `commandForCall()`
  recovers the command from the streamed call.
- **Sandbox modes and presets** (`dsh-sandbox-policy`,
  `dsh-permission-presets`): `read-only`, `workspace-write`,
  `danger-full-access`, switched with `/permission`. **Plan mode**
  (`dsh-plan-mode`): `/plan`, `/plan off`. All mounted by `dsh-base`.
- **Instructions** (`dsh-agent-instructions`, mounted by `dsh-base`):
  `$DSH_HOME/AGENTS.md`, then `AGENTS.md`/`CLAUDE.md` (+ `.local.md`
  overlays) from the `.git` root down to the cwd, 64 KB budget. Refreshes only
  after file-tool activity or on resume.
- **Seams for new behavior:** `ctx.tools.register(defineTool(...))` for
  tools, `ctx.systemPrompt.section({ name, order, text })` for prompt text,
  `tools/pre-execute` for allow/deny/ask with arguments in hand.

## Part A — Permissions

### A1. Approval panel with four choices (`src/tui/panels.ts`, `src/index.ts`)

```
Allow bash?
  git log --oneline -20
  1 Allow once
  2 Allow for this session
  3 Always allow  bash(git log *)  [project ▾]   ← pattern editable, tab toggles project/global
  4 Deny                                          ← esc still denies
```

- A matching rule is answered in moqi's existing listener before any panel
  opens, returning `allowed-once`, so the Harness audit log still records every
  decision.
- **Arguments come from the session log, not from `detail`.** `detail`
  (`describeToolCall`) is a display summary — whitespace folded, capped at 200
  chars, partial JSON mid-stream — so a newline-separated `rm` can hide behind
  it. The listener scans `request.agent.session` backwards for the `tool/call`
  event with the request's `callId` (or `tool/ptc-dispatch-start` with a
  matching `subCallId` for calls nested in `run_code`), parses its `arguments`,
  and matches the exact `command`. The Harness appends that event before any
  ask, so it is always there; if it is not found, show the panel.
- **Escalations name their mode.** Most bash asks are the model requesting
  sandbox escalation (`reason` = `escalate sandbox to <mode>: …`). A rule saved
  from such an ask records the target mode — `bash(git log *) @
  danger-full-access` — and only answers asks for that mode or a narrower one.
- Fix while here: `commandForCall` searches the on-screen tab, not the tab that
  asked, so an ask from a background session shows no command.
- Subagents need nothing: `dsh-subagent` pins their approval policy to
  `never`, so their asks never reach moqi. Terminal, persistent shells, and MCP
  tools only ask via hooks.
- An auto-allowed call's tool row says so: `✓ allowed by rule bash(git log *) · project`.
- Rewrite the "no 'always' temptation" comment on `ApprovalPanel`.

### A2. Rule store (`src/permissions.ts`, pure, testable offline)

| Scope | Lives in | Lifetime |
|---|---|---|
| session | memory, on the `SessionTab` | until the tab closes |
| project | `~/.dsh/moqi/permissions/<projectKey>.yaml` | durable |
| global | `~/.dsh/moqi/permissions/global.yaml` | durable |

```yaml
version: 1
allow:
  - tool: bash
    command: git log *
  - tool: read_file
```

Allow rules only — no deny rules in this release.

**Project rules live outside the repo, not in `<repo>/.dsh/`.** A committed
rules file in a cloned repo could silently grant `bash *` to whoever opens it;
keeping them under `~/.dsh`, keyed by `projectKey()`, removes that path.

### A3. Matching — the security-sensitive part

- Non-shell tools: match on tool name.
- Shell tools (bash, persistent bash, pwsh, terminal): match the command
  against a token-wise glob prefix. Default suggestion is the first two tokens
  (`git log *`, `npm test *`); one token when the second is a flag or path.
- Compound commands (`&&`, `||`, `;`, `|`, newline) auto-allow only if
  **every** segment matches.
- Never auto-allow anything containing `$(…)`, backticks, `<(…)`/`>(…)`,
  or a redirect (`>`, `>>`) whose target is outside the workspace.
- If the command cannot be recovered, always show the panel.
- As built: redirects are refused except fd duplication (`2>&1`) and
  `/dev/null`; any `<` and unquoted parentheses are refused; matching is
  case-sensitive.
- **Known limit, shared with Claude Code's `Bash(git log:*)`:** a prefix rule
  bounds the *command*, not its flags — `git log *` also matches
  `git log --output=/etc/passwd`, `find *` matches `find . -exec …`. The
  panel's suggested pattern should stay narrow, and a later release could add a
  per-command deny list of side-effecting flags.

### Interface for the wiring (built)

The approval listener talks to one `PermissionRules` per session
(`src/permissions.ts`): `decide({ toolName, args, reason })` with the
`tool/call` event's raw arguments, `suggest(...)` for the panel's "always"
row, `grant/revoke(rule, scope)`, and `list()` for `/permissions`. It reads
the files on every decision, so grants and hand edits apply across sessions
at once.

### A1 status (built)

Wired and verified live against dsh: a sandbox-denied write, escalated by the
model, opened the four-row panel; "this session" kept `bash(touch *) @
danger-full-access`, and the next escalated `touch` was answered by the rule
with no panel, both decisions in the Harness audit log. The auto-allow shows on
the status line; marking the tool row itself is still to do. Found on the way:
with tiled view saved and one session open, moqi dropped every panel
(pre-existing on `main`) — fixed with one `tilesOnScreen()` predicate.

### A4 status (built)

`/permissions` is a grouped picker over `PermissionRules.list()` (session /
project / everywhere), `enter` revokes after a y/n confirm, and two rows open
the project or global rules file in `$EDITOR` (via a shared `runEditor` the
draft editor now uses too). Verified live with a stand-in editor: empty list,
valid edit listed, revoke confirmed, malformed edit reported as "rules off".

### A4. `/permissions`

One panel listing session, project, and global rules; `d` deletes the selected
rule, `e` opens the scope's file in `$EDITOR`.

### A5. Mode cycle on `shift+tab` (`src/tui/keys.ts` decodes `\x1b[Z`)

Cycles **read-only → workspace-write → plan** via the Harness's own presets and
plan mode. `danger-full-access` is deliberately not in the cycle — it takes an
explicit `/permission danger-full-access`. Footer shows a mode badge, separate
from the vim badge.

## Part B — Memory

### B1. Agent-written memory

- **Store:** `~/.dsh/memory/` (global) and
  `~/.dsh/memory/projects/<projectKey>/` (project). Each holds a `MEMORY.md`
  index (one line per memory: `- [Title](slug.md) — hook`) plus one
  `<slug>.md` per fact with front matter `name`, `description`, `type`
  (`user | feedback | project | reference`).
- **Tools:** `memory_save`, `memory_read`, `memory_forget`, registered with
  `defineTool`. Slugs are sanitized so a write cannot escape the memory
  directory; no sandbox prompt is involved.
- **Injection:** a `moqi:memory` prompt section carrying **only the index**,
  capped (~200 lines / 8 KB, broad entries dropped first). The model reads a
  fact with `memory_read` when it is relevant.
- **Prompt-cache stability:** the index is snapshotted once per session and
  refreshed only on a new session or after `/compact`; saves made mid-session
  report through their tool result instead of rewriting the system prompt.
- **Gate:** `/memory auto on|off`, persisted with moqi's state.

### B1 status (built)

`src/memory-tools.ts` registers `memory_save` / `memory_read` /
`memory_forget` per agent over the tab's `MemoryStore` (read at call time, so a
resumed session writes to its own project), and a `moqi:memory` section at
order 10100 holding `promptIndex()` captured on the first request, then frozen.
Verified live: saved in one session, listed by a new session with no tool
call, then read back with `memory_read`. Not built: the `/memory auto` gate.

### B2. `/memory` panel

Top half: the instruction chain the Harness is actually loading (global
`AGENTS.md`, then each project file root → cwd). Bottom half: the memory
index. `enter` opens in `$EDITOR`, `d` deletes a memory, `n` creates a missing
`~/.dsh/AGENTS.md`. The panel notes that an edited `AGENTS.md` is picked up
after the next file-tool activity or a resume.

### B3. `# ` quick-add

A single-line composer entry starting with `# ` is not sent. A small picker
asks where it goes — project memory / global memory / project `AGENTS.md` /
global `AGENTS.md` — and appends it. Multi-line pastes send normally.

## Part C — Branches and worktrees (built)

Isolation is the default: a new session in a git repo starts on its own
`moqi/<date>-<id>` branch, in place (no copy). `/worktree <name>` opens a
session in `$DSH_HOME/worktrees/<projectKey>/<name>`; `/branch <name>`
switches the current session; `/isolation` / `--isolation` choose
`off|branch|worktree`. `/close` removes only a branch with no commits of its
own and a clean worktree. Pure logic in `src/git-workspace.ts`, wired in
`src/index.ts`; user docs in `docs/using-moqi.md#branches-and-worktrees`.
